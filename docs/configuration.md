# Charon Configuration

This document describes the configuration options for running a charon node and cluster locally or in production.

## Cluster Config Files

A charon cluster is configured in two steps:
- `cluster-definition.json` which defines the intended cluster configuration without validator keys.
- `cluster-lock.json` which includes and extends `cluster-definition.json` with distributed validator BLS public key shares.

The `charon create dkg` command is used to create `cluster-definition.json` file which is used as input to `charon dkg`.

The `charon create cluster` command combines both steps into one and just outputs the final `cluster-lock.json` without a DKG step.

The schema of the `cluster-definition.json` is defined as:
```json
{
  "name": "best cluster",                       // Cosmetic cluster name
  "creator": {                                  // Creator of this cluster definition
    "address": "0x123..abfc",                   // ETH1 address of the creator
    "config_signature": "0x123456...abcdef"     // EIP712 Signature of config_hash by ETH1 address. Proves that the creator created the config.
  },
  "operators": [                                // Operators of all Charon nodes in the cluster
    {
      "address": "0x123..abfc",                 // ETH1 address of the operator
      "enr": "enr://abcdef...12345",            // Charon node ENR
      "config_signature": "0x123456...abcdef",  // EIP712 Signature of config_hash by ETH1 address. Proves that the operator accepts the config.
      "enr_signature": "0x123654...abcedf"      // EIP712 Signature of ENR by ETH1 address. Allows this ENR to act on behalf of the operator.
    }
  ],
  "uuid": "1234-abcdef-1234-abcdef",            // Random unique identifier.
  "version": "v1.3.0",                          // Schema version
  "timestamp": "2022-01-01T12:00:00+00:00",     // Creation timestamp
  "num_validators": 100,                        // Number of distributed validators to be created in cluster.lock
  "threshold": 3,                               // Threshold required for signature reconstruction
  "validators": [                               // Metadata related to each validator to be created
    {
      "fee_recipient_address":"0x123..abfc",    // ETH1 fee recipient address
      "withdrawal_address": "0x123..abfc"       // ETH1 withdrawal address
    }
  ],
  "dkg_algorithm": "foo_dkg_v1" ,               // DKG algorithm for key generation
  "fork_version": "0x00112233",                 // Chain/network identifier
  "deposit_amounts": [                          // Partial deposit amounts in gwei (must sum up to at least 32ETH)
    "16000000000",
    "16000000000"
  ],
  "config_hash": "0xabcfde...acbfed",           // Hash of the initial configuration fields excluding operator ENRs and signatures
  "definition_hash": "0xabcdef...abcedef"       // Final hash of all fields (after all operators have added ENRs and signatures)
}
```

See the [cluster.Definition](../cluster/definition.go) and [cluster.Operator](../cluster/operator.go) Go structs for
details on how this `cluster-definition.json` object is (de)serialised and how the [SSZ](https://github.com/ethereum/consensus-specs/blob/dev/ssz/simple-serialize.md)
config hash and definition hash are calculated.

The creator `config_signature` and operator `config_signature` and `enr_signature` are [EIP712](https://eips.ethereum.org/EIPS/eip-712) signatures of **typed structured data** as opposed to just raw bytes. EIP712 enables users to see the object that they are signing in their wallet (ex: Metamask).
See [eip712sigs.go](../cluster/eip712sigs.go) for details on the EIP712 structure used to create these signatures.

The above `cluster-definition.json` is generated by the [dv-launchpad](https://launchpad.obol.org/) provided as input to the `charon dkg` command which generates keys and the `cluster-lock.json` file.

The `cluster-lock.json` has the following schema:
```json
{
  "cluster_definition": {...},                              // Cluster definition json, identical schema to above,
  "distributed_validators": [                               // Length equal to num_validators.
    {
      "distributed_public_key":  "0x123..abfc",             // DV root pubkey
      "public_shares": ["0x123..abfc", "0x123..abfc"],      // The public share of each operator (length of num_operators)
      "partial_deposit_data": [...],                        // Deposit datas to activate this validator (corresponds to deposit_amounts)
      "builder_registration": {...}                         // Pre-generated signed builder registration for the validator
    }
  ],
  "deposit_amounts": [                                      // Partial deposit amounts in gwei (must sum up to at least 32ETH)
    "16000000000",
    "16000000000"
  ],
  "lock_hash": "0xabcdef...abcedef",                        // Hash of the cluster definition and distributed validators. Uniquely identifies a cluster lock.
  "signature_aggregate": "0xabcdef...abcedef",               // BLS aggregate signature of the lock hash signed by all the key shares of all the distributed validators. Proves that the key shares exist and attest to being part of this cluster.
  "node_signatures": ["0xabcdef...abcedef"]                 // Signatures of the lock hash by each operator. Proves that this lock file (and the validators) was generated by all the operators
}
```

`charon run` just requires a `cluster-lock.json` file to configure the cluster. See the [cluster.DepositData](../cluster/deposit.go) and [cluster.BuilderRegistration](../cluster/registration.go) Go structs for more details
on how an individual `distributed_validator` looks like.

### Cluster Config Change Log

The following is the historical change log of the cluster config:
- `v1.10.0` **default**:
  - Added the `target_gas_limit` field to cluster lock which contains the preferred target gas limit for transactions.
  - When not specified, the default value of `36000000` will be used.
  - Added the `compounding` flag to cluster lock which enables compounding rewards for validators by using 0x02 withdrawal credentials.
- `v1.9.0`:
  - Added the `consensus_protocol` field to cluster lock which contains the preferred consensus protocol for the cluster.
  - When not specified, the default value of `qbft` will be used.
- `v1.8.0`:
  - Added the `deposit_amounts` list to the cluster lock, which contains partial deposit amounts in gwei.
  - When specified, the sum of the partial amounts must be between 32 ETH and 2048 ETH.
  - When not specified, it generates deposits for 1 ETH and 32 ETH amounts.
  - `distributed_validator` structure replaced `deposit_data` with `partial_deposit_data` respectively.
- `v1.7.0`:
  - Added the `builder_registration` structure to `distributed_validators` list in cluster lock.
  - This enables distributed validators to submit pre-generated validator registrations that enable MEV-blocks.
  - Added the `node_signatures` list to cluster lock which contains signatures of the lock hash signed by each individual node.
- `v1.6.0`:
  - Add `deposit_data` structure to `distributed_validators` list in cluster lock.
  - This allows anyone with access to the lock file to activate the validators, specifically, the **creator**.
- `v1.5.0`:
  - Add the `validators` list to cluster definition that contains `fee_recipient_address` & `withdrawal_address` for each validator.
  - This allows configuring multiple fee recipient and withdrawal addresses instead of a single address for all validators.
- `v1.4.0`:
    - Added the `creator` nested structure to the cluster definition proving who created the cluster definition (including non-operators).
    - Refactored operator `config_signature` EIP712 structure to distinguish between operator and creator `config_signatures`.
- `v1.3.0`:
    - Refactored `config_hash`, `definition_hash` and `lock_hash` calculations by aligning with SSZ common types:
        - `ByteList[MaxN]`: Variable length with max limit for strings.
        - `BytesN`: Fixed length byte.
        - `Uint64`: numbers.
    - Refactored definition operator signatures: `config_signature` and `enr_signature` to use updated EIP712 structured types.
    - This version is compatible with [dv-launchpad](https://github.com/ObolNetwork/dv-launchpad) generated `cluster-definition.json`.
    - See example [definition.json](../cluster/testdata/cluster_definition_v1_3_0.json) and [lock.json](../cluster/testdata/cluster_lock_v1_3_0.json)
- `v1.2.0`:
    - Refactored all base64 fields to Ethereum's standard 0x prefixed hex.
        - Refactored definition operator signatures: `config_signature` and `enr_signature`.
        - Refactored definition fields: `config_hash` and `definition_hash`.
        - Refactored lock fields: `lock_hash`, `signature_aggregate` and `distributed_validators.public_shares`.
    - Remove definition operator `nonce` field since it isn't used for anything. Only support `nonce=0` for older versions.
    - See example [definition.json](../cluster/testdata/cluster_definition_v1_2_0.json) and [lock.json](../cluster/testdata/cluster_lock_v1_2_0.json)
- `v1.1.0`:
    - Added cosmetic `Timestamp` field to cluster definition to help identification by humans.
    - See example [definition.json](../cluster/testdata/cluster_definition_v1_1_0.json) and [lock.json](../cluster/testdata/cluster_lock_v1_1_0.json)
- `v1.0.0`:
    - Initial definition and lock versions.
    - See example [definition.json](../cluster/testdata/cluster_definition_v1_0_0.json) and [lock.json](../cluster/testdata/cluster_lock_v1_0_0.json)

This version of Charon (logic) supports the following cluster config versions (files): `v1.0.0`, `v1.1.0`, `v1.2.0`.

## Proposer Config

From the gloas fork onwards charon and the validator client take their fee recipients, gas limit and builder
settings from `vc-config/proposer-config.json` (default `.charon/vc-config/proposer-config.json`, `--proposer-config-file`).
The file is a revisioned document, signed by the cluster operators:

- **Revision 0** is unsigned. With no file, `charon run` writes revision 0 from the cluster lock, the builder registration
  overrides file (`--overrides-file`) for the fee recipients, falling back to the lock's,
  and the `--proposer-config-*` seeding flags for the gas limit and builders. At revision 0 the file wins: seeding flags that differ
  from it only produce a warning naming `charon alpha proposer edit`. After the gloas fork charon also warns that an unsigned file is in use.
- **Revision 1 and higher** carry the signatures of at least the cluster threshold of operators over the revision hash,
  made with their charon ENR keys and verified on start against the operator ENRs in the lock. Once the file is signed the seeding flags
  are disregarded, with a warning if flags you set explicitly differ from it.

The first signed revision takes its gas limit and builders from the `--proposer-config-*` flags of `charon dkg` and
`charon create cluster`, or from a seed file passed to either with `--proposer-config-seed-file` (a path or an HTTP URL), never both.
`charon create dkg` writes the seed file as `proposer-config-seed.json` next to `cluster-definition.json` when given any
`--proposer-config-*` flag, filling the ones left out with their defaults, so whoever creates the definition sends both files
to every operator; with `--publish` only the definition is published, the seed file is still sent by hand. The seed's gas limit
is `--proposer-config-gas-limit`, independent of the definition's `--target-gas-limit`, which only sets the gas limit of the
builder registrations and is deprecated from the gloas fork onwards, when those are no longer sent. The file is the `version` and `default_config`
of the proposer config file without a fee recipient, which always comes from the definition; the `builder` block is left out
when there are no builders:

```json
{
  "version": "v1.0.0",
  "default_config": {
    "gas_limit": "200000000",
    "builder": {
      "min_bid": "0",
      "builder_boost_factor": "100",
      "max_execution_payment": "0",
      "builders": [ { "url": "https://builder-a.example" }, { "url": "https://builder-b.example" } ]
    }
  }
}
```

On start, a file whose `lock_hash` belongs to another cluster stops charon. A file with invalid revision or signatures is logged as an error,
raises `app_proposer_config_invalid` to 1 and is still used (the validator client reads it regardless). A file that cannot be loaded
at all, or holds values charon cannot parse (e.g. a non-numeric gas limit), is left untouched, logged as an error with `app_proposer_config_invalid` at 1,
and charon uses the content derived from the lock and flags in memory meanwhile; delete it to have charon regenerate revision 0 on the next start.
This includes a file with `"version": 1` written by a v2.0.0 release candidate. Charon reloads the file at runtime when it is replaced,
for example by an edit ceremony; the validator client only picks the new file up once its settings are rendered again and it is restarted, see below.

The first signed revision is created together with the cluster, by `charon dkg` and `charon create cluster`, and by the
lock-changing `charon alpha edit` commands (add/remove/replace operators, add validators, recreate private keys), which carry the
current content over into a file signed for the new lock, written to `<output-dir>/vc-config/proposer-config.json`. It replaces the current
`vc-config/proposer-config.json`: switch to the whole output directory, including its `vc-config/`, since charon refuses to start with a
file signed for the previous lock.

### Showing and changing the proposer config

`charon alpha proposer` shows the cluster's proposer config: its revision and the operators that signed it, the default fee
recipient, the gas limit and the builders, as scheme and host only since builder URLs may carry credentials. A missing
file is reported. A file that cannot be read or does not verify against the lock is an error, its content is not shown.
`charon alpha proposer list [--json]` lists the default fee recipient and gas limit and only the validators whose fee recipient
differs from it. Both read
the proposer config file of any of the cluster's nodes and need no node key.

Changing it is a ceremony, like a DKG: one operator running it alone changes nothing. The participating operators agree on a
time, then all run the same command at the same time, which waits for the others to join:

```sh
charon alpha proposer edit \
  --validator-public-keys=0xabc...,0xdef... --fee-recipient-addresses=0x123...,0x456... --gas-limit=60000000 \
  --builder-urls=https://a.example,https://b.example --builder-boost-factor=110
```

At least one change flag is required, the flags combine into one revision, and a flag left out changes nothing:

- `--validator-public-keys` (DV public keys) with `--fee-recipient-addresses` changes the fee recipient of the listed validators, paired
  in list order: the lists must be the same length. `--all` with a single address in `--fee-recipient-addresses` changes every validator,
  those with their own fee recipient included.
- `--gas-limit`, cluster-wide, greater than zero.
- `--builder-urls` (replaces the list, order is the preference order, no duplicates), `--builder-min-bid`, `--builder-boost-factor`,
  `--builder-max-execution-payment`; the last three need an existing builder block or `--builder-urls`. `--no-builders` removes the builder block.

Each operator sees the differences against the current revision and its hash, and confirms them before signing; `--yes` signs
without asking, for scripts, and is required without a terminal.

To spare every operator retyping the same flags, one person creates a proposal file with
`charon alpha proposer create --output-file=proposal.json` and the same change flags, as `charon create dkg` creates the
cluster definition every operator runs the DKG with. It needs the cluster lock and the proposer
config file of any node, which must exist, but no node key, so the author need not be an operator, and it changes nothing. Every operator then
runs `charon alpha proposer edit proposal.json` (a path or an HTTP URL) in place of the change flags; operators passing the file and
operators passing the equal flags agree. An existing file is not overwritten. The proposal file has the seed file's shape and is
complete on its own: it adds the `lock_hash`, the `revision` it proposes, the default `fee_recipient` and a `proposer_config`
keyed by DV public key (not by a node's public shares, as `proposer-config.json` is) for the validators with another fee
recipient. Write it with `create` rather than by hand: a fee recipient left out is refused, not defaulted. A file for another
cluster, or for a revision other than the next one, is refused, so a stale file cannot revert a later change; the file `create`
reads must hold the cluster's latest revision. Builder URLs are logged redacted, so check them in the file itself.

`--participating-operator-enrs` lists the operators running the ceremony, this node included, as for `remove-operators`. It defaults
to all operators and must list at least the cluster threshold; every participant passes the same list. An operator that missed a ceremony shows up as `app_peerinfo_proposer_config_mismatch` on its peers and catches up by joining the next edit ceremony, where it adopts the newer signed revision from its peers.
The hidden `--timeout` (default 24h) is how long to wait for the other operators to join, `--p2p-relays` defaults to
`https://4.relay.obol.dev`. Use relays that do not serve your running charon node. The ceremony connects via relays only, it neither
listens nor advertises addresses. Run inside charon's container, the command inherits charon run's environment, including the
`CHARON_P2P_RELAYS` your node uses, so pass `--p2p-relays` explicitly:

```sh
docker compose exec charon charon alpha proposer edit --p2p-relays=https://4.relay.obol.dev --gas-limit=60000000
```

On success the ceremony writes revision N+1 and archives the previous file as `proposer-config-revision-<N>.json` next to it.
To apply the new file, rerun `charon alpha vc-bundle`, move the files and restart the validator client: a restart alone keeps the
old settings. On charon-distributed-validator-node the `vc-bundle` service does the rendering, and
`docker compose restart <vc service>` does not run it: recreate the validator client's container instead. Before the gloas fork
charon's own builder registrations are unaffected, and a fee recipient change also needs `charon feerecipient sign` and `fetch`.

### Validator client files

Two commands write what a validator client consumes from this node's cluster artifacts, each for one client:
`<teku|prysm|lodestar|nimbus|lighthouse>`.

- `charon alpha validator config <client>` writes the client's proposer settings and flags from
  `vc-config/proposer-config.json` to `--output-dir` (default `.charon/validator-config/<client>`). It holds no keys.
  From the gloas fork builders are enabled exactly when the proposer config has a builder block. Before it the proposer
  config has none and charon's builder API serves them: pass `--builder-api` as for `charon run`, which enables builder
  proposals on Teku, Prysm, Lighthouse and Nimbus without a builder block.
- `charon alpha validator keys <client>` copies the key shares of `validator_keys/` into the client's layout, to
  `--output-dir` (default `.charon/validator_keys/<client>`, beside the originals, which stay unchanged).

| Client | `validator keys` | `validator config`: proposer settings | `validator config`: `vc-flags.txt` |
|---|---|---|---|
| Teku | `keystores/keystore-N.json`, `keystores/keystore-N.txt` | `teku-proposer-config.json`, builders included (read by Teku from 26.11.0) | `--Xobol-dvt-integration-enabled` |
| Prysm | `prysm-wallet/direct/accounts/all-accounts.keystore.json`, `prysm-wallet/walletpassword.txt` | `prysm-proposer-settings.json`, with an entry for every validator | `--distributed`, `--enable-beacon-rest-api` |
| Lodestar | `keystores/<pubkey>/voting-keystore.json`, `secrets/<pubkey>` | `lodestar-proposer-settings.yml` | `--distributed`, `--payloadLocal=true`, `--builder.selection=maxprofit`, `--allowDangerousTrustedPayments` with a max execution payment above 0 |
| Nimbus | `validators/<pubkey>/keystore.json`, `secrets/<pubkey>` | `validators/<pubkey>/suggested_fee_recipient.hex`, `suggested_gas_limit.json` | `--distributed`, `--doppelganger-detection=false`, `--payload-builder`, one `--payload-builder-url` per builder and `--builder-*` |
| Lighthouse | `validators/<pubkey>/voting-keystore.json`, `secrets/<pubkey>` | `validators/validator_definitions.yml`, `validators/builder_definitions.yml` (no builders without a builder block) | `--distributed` |

`vc-flags.txt` holds the flags a distributed validator needs, one per line, to append to the validator client's command;
the builder flags are only written with a builder block, Nimbus's `--payload-builder=true` also with `--builder-api`. Paths, the network, the beacon node and metrics stay the operator's.
Nimbus and Lighthouse read their settings from the directory holding their keys, so both commands' `validators/` directories
go into the same one. Lighthouse's definitions name the keystores by absolute path under `--lighthouse-dir`, its data directory as Lighthouse
sees it (e.g. `/root/.lighthouse/hoodi` in its container), so move `validators/` and `secrets/` there. Prysm only reads keys from a wallet, so its key shares are decrypted into one, encrypted with a new random
password that Prysm reads from the wallet directory: point `--wallet-dir` at it, no import needed. The commands log the
client version the files are made for: Teku `26.11.0`, Prysm `v7.3.1`, Lodestar `v1.50.1`, Nimbus `v26.10.2`, Lighthouse `v8.3.3`. Rerun `validator config` after the proposer config changes, then restart the validator client.

## Flag Precedence

Charon uses [viper](https://github.com/spf13/viper) for configuration combined with [cobra](https://github.com/spf13/cobra)
for cli commands.

In descending order, the Charon node checks the following places for configuration:
- From environment vars beginning with `CHARON_`, with hyphens substituted for underscores. e.g. `CHARON_BEACON_NODE=http://....`
- From the config file specified with the `-config-file` flag as YAML, e.g. `beacon-node: http://...`
- From CLI params, e.g. `--beacon-node http://...`
